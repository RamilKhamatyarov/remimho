# Design

## Context

See proposal.md for motivation. Facts observed in the code that shape the approach:

- The 2D reducer (`service/mvi`) is pure and already takes `PhysicsRules` explicitly. Its state
  (`MviGameState`) is made of `Double` fields. It calls `kotlin.math` `sin`/`cos` (8 each),
  `atan2` (2), `hypot` (14) and `StrictMath.pow` (1). `kotlin.math` maps to `java.lang.Math`,
  which HotSpot may replace with per-architecture intrinsics; `StrictMath` may not be replaced.
  Whether this actually diverges between x86-64 and ARM64 is unknown, and is what the audit
  measures. It is a hypothesis until hashes show it.
- 2D ticks carry variable durations in nanoseconds (`ReplayTick`). ADR 0017 already concedes that
  different tick partitions are not byte-identical.
- Determinism is currently tested by one SHA-256 over serialized bytes in `SpinReplayTest`, on
  one platform. There is no per-tick hash and no cross-architecture check.
- The simulation runs only on the server JVM. The browser renders; it does not simulate.
- CI (`.github/workflows/ci.yml`) runs on x86 runners only. `HeadlessReplayImporter` is the
  existing headless reduction path. `docs/demo.gif` is regenerated by local `build`.
- The "earlier draft" of the tunnel mechanics referred to in the request is not in the
  repository. This design fixes the structure of the physics; numeric constants are set during
  implementation and are then pinned by the golden traces.

Decisions already made with the user: one change covering all seven steps with a hard gate before
physics; second platform is JVM ARM64; 2D is audit-only; substrate chosen after the audit; fixed
timestep for 3D; standalone tape format; hashing headless only; ARM parity through a CI job; the
3D button, rendering and protocol are a follow-up change.

## Goals / Non-Goals

**Goals:**

- A hash and trace toolchain that works on the 2D state first, so it is proven on real code
  before any 3D code exists.
- A 3D core whose every state-affecting operation is exactly defined, so parity is a property of
  the design and the CI job only confirms it.
- Zero behavioral change to live rooms and to replay versions 1-3.

**Non-Goals:**

- Bit parity between the JVM and a browser or native image.
- Making 2D bit-deterministic across architectures. The audit reports; it does not fix.
- Any live wiring of the tunnel mode: no room actor, WebSocket, protobuf state or frontend work.
- Hash stability across future changes to the state shape. A hash is comparable only between
  runs of the same code version; goldens are regenerated when state fields change.

## Decisions

### D1. Package layout: new packages, nothing added to `service/mvi`

- `ru.rkhamatyarov.determinism`: `StateHasher`, canonical encoders, trace model, trace diff,
  CLI entry points.
- `ru.rkhamatyarov.tunnel`: numerics facade, state, reducer, tape reader/writer.
- `src/main/proto/tunnel_tape.proto`.

The 2D encoder (`MviGameState` to canonical fields) lives in `determinism`, reading the public
state. *Alternative:* a `hash()` method on `MviGameState`. Rejected: it touches the 2D model the
user asked to leave alone and couples state to a diagnostic.

### D2. Canonical field stream, FNV-1a 64 over it

State is written to a `FieldSink` as an ordered stream of `(path, typed value)` pairs by a
hand-written encoder per state type. Rules:

- Fixed field order defined by the encoder, never by reflection or `hashCode`.
- `Double` as `toRawBits()` little-endian, with every NaN mapped to one canonical pattern;
  `-0.0` and `0.0` stay distinct because they can steer later arithmetic (`atan2`, division).
- `Long`/`Int` little-endian fixed width; `Boolean` one byte; enums by stable name, strings as
  length-prefixed UTF-8; lists as length then elements in list order; maps and sets sorted by key.
- Fixed-point values, if chosen in D5, as their raw `Long`.

Two sinks consume the same stream: `HashSink` (FNV-1a 64, integer-only, so trivially identical on
every architecture) and `DumpSink` (path plus exact value in hex), which is what the diff tool
compares. One encoder feeding both guarantees the dump and the hash can never disagree about
which fields count.

A completeness test guards the encoders: it reflects over the state class's constructor
properties and fails when a property is neither encoded nor listed in an explicit
"presentation-only" exclusion list. Adding a state field therefore forces a decision.

*Alternatives:* hashing protobuf bytes (rejected: proto serialization is not canonical, and it
would hash the mapper, not the state; `GameStateMapper` already truncates `remainingSeconds`);
SHA-256 truncated to 64 bits (works, but slower per tick and no stronger for a diagnostic);
xxHash64 (faster, more code, no benefit at this scale).

### D3. Trace format and where hashes are taken

A trace is a text file: a header (tape or replay identity, physics version, substrate, code
revision, architecture, JVM) then one line per step, `step hash16`. Text keeps golden diffs
readable in review. For 2D, `HeadlessReplayImporter` gets an optional per-tick observer; with no
observer its behavior and cost are unchanged. Live rooms never install one.

### D4. 2D audit method

A Gradle task `determinismAudit` (not attached to `build`) reduces a corpus and writes traces to
`build/determinism/`:

- Corpus: `src/test/resources/demo.replay` plus generated 2D recordings that concentrate on the
  suspect operations: steep and shallow bounce angles (`sin`/`cos`), line collisions (`atan2`),
  rabbit turns, long spin decay (`StrictMath.pow`), near-tangent edge hits, extreme speeds.
  Generators are deterministic integer-seeded scripts committed as test fixtures.
- Dimensions: (a) two fresh processes on one machine; (b) interpreter-only (`-Xint`) versus
  default JIT on one machine, because intrinsics are a JIT feature; (c) x86-64 versus ARM64.
- Reference traces from x86-64 are committed under `src/test/resources/determinism/2d/`.
- The report `docs/determinism/2d-audit.md` lists every state-affecting floating-point operation
  by file and classifies it (exact IEEE basic op, `StrictMath`, or `Math` and possibly
  intrinsic), then gives per-recording results for (a), (b), (c) with hashes and, on divergence,
  first tick and differing fields from the diff tool.

The diff tool is therefore built before the audit report is finished, although the request lists
it fifth: the audit needs it to name divergence points. Ordering in tasks.md reflects that; the
gate before physics is unaffected.

### D5. Substrate: strict IEEE subset selected from ARM64 parity evidence

Evidence amendment (2026-11-17): ARM64 run 44112987043 passed the blocking vector check and the
report-only comparison of all 12 2D traces. The successful trace step compares every per-step hash
and trace length with committed x86-64 references. The manifest writer maps the successful step to
`traceParity=pass`; its artifact was uploaded. These results make a strict IEEE subset admissible
and preferred for future tunnel physics: basic `Double` operations only, `StrictMath` or specified
integer algorithms for non-basic operations, and no `Math.fma`. This is empirical evidence for
the tested corpus and JVM builds, not a universal proof. [ADR 0018](../../adr/0018-tunnel-numerical-substrate.md) records the decision and its
remaining runtime-metadata limitation.

The pre-existing Q32.32 facade and vectors remained scaffolding until implementation. They were
explicitly retained for tunnel physics by [ADR 0019](../../adr/0019-tunnel-physics-mechanics.md),
which also opens gate 7.1; the strict IEEE subset remains the direction for a future 2D migration.

Tunnel arithmetic remains behind a package-local facade. [ADR 0019](../../adr/0019-tunnel-physics-mechanics.md)
explicitly retains the `TunnelMath` Q32.32 implementation for the tunnel physics. The substrate
choice remains confined to one package:

| Candidate | Exactness | Cost |
| --- | --- | --- |
| Fixed-point (`@JvmInline value class Fx(val raw: Long)`, Q32.32, integer-only `sqrt`, table or CORDIC trig) | Exact by construction | Overflow and range analysis; own trig; 2D migration would be a rewrite |
| Strict IEEE subset (`Double` with only `+ - * /` and `sqrt`, everything else through `StrictMath` or own polynomials, no `Math.fma`) | Exact if the JVM honors IEEE for the basic ops (it does since strictfp became default in Java 17) | Discipline enforced by a lint test; relies on the JVM claim, which the audit tests |
| Software floating-point (soft-float on `Long`) | Exact by construction | Slowest; most code; no advantage over fixed-point here |

Decision criteria, applied to audit evidence:

1. If basic `Double` operations show any cross-architecture divergence, choose fixed-point.
2. The tested traces match, so use the strict IEEE subset for the new tunnel. Any future substrate
   vector or physics-trace divergence requires revisiting the decision; replay versions 1-3 remain
   unaffected.
3. [ADR 0018](../../adr/0018-tunnel-numerical-substrate.md) states the 2D migration cost: call sites to change, and that it requires
   replay version 4 with versions 1-3 kept on their current arithmetic.

A source-scan test fails the build if anything under `ru.rkhamatyarov.tunnel` imports
`kotlin.math`, `java.lang.Math`, `Random`, or reads a clock. Substrate operation vectors (inputs
and exact expected outputs) are committed and run on both architectures.

*Alternative:* pick fixed-point now. Rejected by the user in favor of deciding on evidence.

### D6. Tape: protobuf header plus length-delimited records

`tunnel_tape.proto` defines `TapeHeader` (format version, physics version, substrate id, step
duration in nanoseconds, tunnel dimensions, initial state) and `TapeRecord` (`kind`, `seq`,
`step`, kind-specific payload). The file is the header followed by length-delimited records, so
appending never rewrites earlier bytes and a cut file still parses up to its last whole record.

Kinds for this change: `PADDLE_TARGET` (side, cross-section position), `SERVE`, `RESET`, and
`MARK` (no payload; pins the step count reached, written periodically and on close, so the tape
says how far to simulate when no input follows). Replay runs to the highest step named.

Payload coordinates are stored in the substrate's own representation (raw fixed-point `Long`, or
`Double` bits), never as decimal text.

*Alternatives:* extending `ReplayFile` (rejected by the user; it also carries per-tick
durations); JSON lines (rejected: decimal round-tripping of numbers is a determinism hazard).

### D7. Fixed timestep

Step duration is a header constant, default 1/120 s expressed in integer nanoseconds. The reducer
signature is `reduceTunnel(state, inputsForThisStep, rules): TunnelState`; there is no delta
time parameter. Converting real time to whole steps is the job of the future room integration and
is outside this change.

### D8. Tunnel physics structure

- Axes: `z` along the tunnel between the two paddles, `x`/`y` the cross-section. Paddles are
  rectangles in the `x`/`y` plane at each end, positioned by `PADDLE_TARGET`.
- Per step, in this fixed order: apply inputs, move paddles toward targets (bounded speed),
  apply spin curve to velocity, sweep the puck through the step resolving the earliest contact
  first (walls, then paddle planes, repeating on the remaining fraction with a hard iteration
  cap), decay spin, detect a goal when the puck passes a paddle plane without contact.
- Spin is a two-component vector in the cross-section plane. The curve is a sideways
  acceleration proportional to spin; decay is per step, which is exact under a fixed timestep.
- Paddle contact is a swept sphere against the paddle rectangle translated by the paddle's own
  movement over the step, following the slab approach of the 2D `PaddlePhysics`. Imparted spin is
  the paddle's cross-section displacement over the step times a gain, clamped to a maximum.
- All constants live in a `TunnelRules` value passed into the reducer, so a test can alter one
  constant and prove the goldens notice, and so a later physics version can coexist.

### D9. Golden fixtures

`src/test/resources/tunnel/golden/<scenario>.tape` and `<scenario>.trace` for: zero-spin wall
bounce, constant-spin curve, known-sweep paddle contact (more may be added). The test replays
each tape and compares every step hash; on mismatch it reports through the diff tool.

- Regeneration is the Gradle task `updateTunnelGoldens` only. Tests never write.
- Each trace header records the tunnel physics version; the test rejects a mismatch, so changing
  physics requires bumping the version and regenerating, both visible in the pull request.
- A mutation test runs the goldens with a `TunnelRules` copy in which one constant is altered and
  asserts failure, once per constant.

The harness and its self-tests are built in step 6 against a trivial stand-in reducer; the real
golden traces can only be produced once the physics exists, so they are generated and committed
as part of step 7 and frozen from then on.

### D10. Gate before physics

`docs/determinism/gate.md` is a checklist of the verification criteria for steps 1-6, each with
a link to its evidence (report, CI run, test name). The gate was ticked on 2026-11-19 once the real
reducer and its goldens existed; see [gate.md](../../../docs/determinism/gate.md).

### D11. ARM64 parity in CI

One new job in `ci.yml`, `runs-on: ubuntu-24.04-arm`, JDK 21, running a Gradle task
`determinismParity` that hashes the committed vectors, replays the committed 2D and tunnel tapes
and compares with the committed x86-64 traces. Until the audit is concluded the 2D comparison is
report-only (`continue-on-error` on that step) so a real 2D divergence produces evidence instead
of blocking every pull request; hash vectors, substrate vectors and tunnel goldens are blocking.

## Risks / Trade-offs

- **The audit finds 2D diverges across architectures** → Expected possibility; it is reported with
  first divergent tick and operation, 2D stays as is, and the migration cost goes into [ADR 0018](../../adr/0018-tunnel-numerical-substrate.md).
- **The audit finds nothing, but divergence exists on untested hardware or JVMs** → The report
  states exactly which CPUs, OS and JVM builds were compared and claims nothing beyond them.
- **GitHub ARM runners are free only for public repositories** → If the repository is private the
  job costs minutes; fallback is a manual run with the trace committed, noted in the report.
- **Fixed-point overflow or precision loss, if chosen** → Range analysis in [ADR 0018](../../adr/0018-tunnel-numerical-substrate.md), checked
  arithmetic in tests, and tunnel dimensions bounded in the tape header validation.
- **Encoder forgets a new state field, so hashes miss a divergence** → Completeness test in D2.
- **Golden traces get regenerated casually to make a test pass** → Separate task, version bump
  required, and traces are text so the diff is visible in review.
- **Golden traces break on every state-shape change** → Accepted; that is the point of a full-trace
  golden. Regeneration is cheap and deliberate.
- **Per-tick observer slows headless import** → It is optional and absent by default; the existing
  importer tests guard the unobserved path.
- **One change is large and long-lived** → Groups 1-6 are each mergeable on their own and add no
  live behavior; the gate keeps physics from starting early.

## Migration Plan

Nothing is deployed to live play. Each task group can be merged independently; rollback is
reverting that group, since no group changes existing behavior. The CI job is added in the group
that first has vectors to check.

## Open Questions

- Exact tunnel constants (dimensions, speeds, spin gain, decay): tuned during implementation,
  then frozen by the golden traces. They do not affect the specs or the task breakdown.
- Whether to add a real-device ARM run (for example Apple silicon) beyond the CI runner: can be
  appended to the audit report at any time.
