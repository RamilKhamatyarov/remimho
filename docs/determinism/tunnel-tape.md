# Tunnel Input Tape

`TunnelTapeWriter` writes a separate, append-only deterministic input format. It does not change or
extend the existing 2D replay protobuf. Each protobuf message is length-delimited, with one header
first and then zero or more records.

## Header

| Field | Meaning |
| --- | --- |
| `format_version` | Tape encoding version; readers currently accept `1`. |
| `physics_version` | Exact simulation rules version required to replay the tape. |
| `substrate_id` | Numeric substrate identifier required by the simulation. |
| `step_duration_ns` | Fixed logical duration of one simulation step; must be positive. |
| `width_raw`, `height_raw`, `depth_raw` | Signed raw Q32.32 values stored in `fixed64` fields. |
| `initial_state` | Serialized initial simulation configuration/state. |

The reader requires explicit sets of supported physics versions and substrate identifiers. A tape
with unsupported metadata is rejected before a reducer is invoked. For the current provisional
substrate, the id is `q32.32-provisional`. The reader rejects blank identifiers, absent initial
state, non-positive dimensions, dimensions above 10,000 units, and step durations outside 1 ns
through 1 s.

## Records

Every record has `kind`, `seq`, and `step`. The writer assigns `seq` starting at one and increments
it for every input and generated marker. The reader rejects gaps, repeats, unknown kinds, malformed
payloads, and decreasing steps. Several inputs at one step retain append order and are passed to the
step reducer in that order. There are no timestamps, durations, connection IDs, or session IDs.

| Kind | Payload | Meaning |
| --- | --- | --- |
| `PADDLE_TARGET` | `paddle_target` | Side plus raw Q32.32 target coordinates. |
| `SERVE` | `serve` | Raw Q32.32 launch velocity components `vx`, `vy`, and `vz`. |
| `RESET` | none | Deterministic reset input. |
| `MARK` | none | Periodic/final complete-step boundary; generated by the writer. |

Markers do not trigger reducer inputs. Replay invokes the reducer once for every logical step,
passing that step's ordered non-marker records, then hashes the resulting state. A tape truncated at
a complete record therefore produces the same hashes through its last complete step as the full
tape.

## Verification

Run the focused tests with:

```powershell
.\gradlew.bat test --tests '*TunnelTapeTest'
```

The tests cover deterministic serialization, periodic and final markers, sequence and step
validation, header and payload validation, unsupported metadata, ordered same-step inputs, and
truncated-prefix replay.

`TunnelGoldenScenarios` contains test-only input-script descriptors for the three planned invariants.
Their tapes use the `tunnel-harness-v1` stand-in identifier and are not physics goldens. The current
reducer applies input records and bounded paddle targets only; it has no puck integration or
collision behavior. The `updateTunnelGoldens` task remains separate and refuses writes without
provenanced ARM64 evidence. Do not generate physics goldens until the real tunnel physics reducer
exists and the parity gate is open.

Once both architectures have produced traces for the same tape and matching physics/substrate
headers, compare the downloaded files with:

```sh
./gradlew traceDiff --args="build/determinism/tunnel-x86.trace build/determinism/tunnel-arm64.trace"
```

Trace diff checks identity headers before comparing hashes. Cross-architecture tunnel parity is
pending external ARM64 verification.
